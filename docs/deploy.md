# Istruzioni di deploy Oracle

## Stato e requisiti

Il package usa sintassi Oracle e richiede almeno Oracle Database 12c per le
colonne `GENERATED BY DEFAULT AS IDENTITY`. Per l'export CSV è richiesto Oracle
SQLcl. SQL Developer può essere utilizzato per l'esecuzione manuale degli altri
script.

Il deploy non è stato ancora eseguito realmente. Queste istruzioni definiscono
la procedura da seguire e non costituiscono evidenza di esecuzione.

## Preparazione dello schema

1. Creare o selezionare uno schema utente dedicato e vuoto.
2. Verificare che l'utente possa creare tabelle, indici e VIEW.
3. Configurare la sessione e i file in UTF-8.
4. Collegarsi senza salvare credenziali negli script o nel repository.

Esempio concettuale di avvio SQLcl, da completare interattivamente con una
connessione autorizzata:

```text
sql <utente>@<servizio_oracle>
```

Non inserire password nella riga di comando, nei file SQL o nei log condivisi.

## Ordine esatto degli script

Eseguire dalla radice del repository:

```text
@sql/01_schema.sql
@sql/02_indexes.sql
@sql/03_dataset.sql
@sql/04_views.sql
@sql/05_queries.sql
@sql/06_tests.sql
@sql/07_export_sqlcl.sql
```

Dipendenze principali:

- tabelle prima di indici e dati;
- dataset prima di query, test e VIEW dimostrativa;
- VIEW prima dei test e dell'export;
- export per ultimo, perché produce un file nel client.

## Gestione degli errori

- considerare bloccanti gli errori `ORA-` durante DDL, INSERT, creazione della
  VIEW o test;
- non ignorare un errore e non proseguire dichiarando un esito positivo;
- distinguere i messaggi informativi SQLcl dagli errori Oracle;
- conservare il log completo della sessione quando viene eseguito il collaudo;
- non modificare il modello per aggirare un errore: applicare il Protocollo di
  modifica dello schema previsto dal Master Workflow.

Se l'esecuzione viene interrotta, non rilanciare ciecamente gli script nello
stesso schema parzialmente popolato.

## Riesecuzione in ambiente pulito

La procedura raccomandata è utilizzare un nuovo schema utente didattico vuoto o
ricreare in modo controllato lo schema di prova secondo le regole
dell'amministratore Oracle. Gli script del progetto non contengono `DROP` e non
eseguono cancellazioni automatiche.

Prima della riesecuzione verificare tramite viste accessibili all'utente che non
siano già presenti gli oggetti omonimi.

## Verifica degli oggetti

Esempi di controlli di sola lettura:

```sql
SELECT table_name
FROM user_tables
ORDER BY table_name;

SELECT view_name
FROM user_views
WHERE view_name = 'VW_EXPORT_NIS2_DEMO';

SELECT constraint_name, constraint_type, status
FROM user_constraints
ORDER BY table_name, constraint_name;

SELECT index_name, table_name
FROM user_indexes
ORDER BY table_name, index_name;
```

L'esito è positivo soltanto se:

- non risultano errori bloccanti;
- sono presenti le 13 tabelle e la VIEW prevista;
- il caricamento termina con i conteggi attesi;
- ogni test di `06_tests.sql` restituisce `OK`;
- `07_export_sqlcl.sql` produce un CSV leggibile.

## Conservazione delle evidenze

Con SQLcl è possibile racchiudere la sessione tra:

```text
SPOOL evidenza_esecuzione.log
-- esecuzione degli script
SPOOL OFF
```

Il log deve essere realmente prodotto e controllato prima di essere indicato
come evidenza. Rimuovere o mascherare eventuali dati di connessione; non
includere credenziali. Il CSV e i log non devono essere simulati.
